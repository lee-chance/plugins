# 결과 검증 및 PR 열기

"컴파일됨"은 증거가 아닙니다. [Prove It Works 원칙](../../skills/principle-prove-it-works/SKILL.md)은 에이전트가 성공을 보고하기 전에 실제 아티팩트를 확인하도록 하며, 당신의 일은 "실제 아티팩트"를 확인 가능하게 만드는 것입니다. 이 페이지는 완료 조건 명시, 측정된 숫자 검증, 앱을 위한 검증 스킬 생성, 테스트가 거의 도달하지 못하는 속성을 공식적으로 검증, PR 열기, 병합까지 주도하는 것을 다룹니다.

검증은 대부분의 에이전트 작업에서 가장 느린 단계인데, 보통 사람을 기다리는 단계이기 때문입니다. 에이전트가 그것을 할 수 있게 만들면, 당신은 병목 현상이 되는 것을 멈춥니다. 건너뛰면, 더 많은 에이전트를 실행하는 것은 검토할 더 많은 확인되지 않은 작업만 얻습니다.

![프로토타입 비행기가 실제 테스트 코스를 비행하는 동안 그녀가 스톱워치로 타이밍하고 로봇들이 실행을 촬영하고 체크리스트; 터미널은 verify: pass, evidence: captured를 읽음.](./images/verification.jpg)

## 완료 조건을 미리 명시

첫 번째 프롬프트에 완료가 무엇을 의미하는지 맞는 단어로 넣으세요:

```text
/poteto-mode add json output to this command. text output stays byte-identical, the json parses, both run against the sample project. show me the evidence.
```

이제 에이전트는 만족시킬 기분이 아니라 실행할 수 있는 세 가지 체크를 가집니다. 답변이 돌아올 때, 정확한 명령과 출력을 전달해야 합니다. 체크가 실행될 수 없다면, 좋은 답변은 "inconclusive"라고 말합니다. 증거 없는 자신감 있는 답변은 경고 신호입니다.

변경에 체크를 매칭하세요:

- CLI 변경은 실제 명령을 실행합니다.
- UI 변경은 실행 중인 앱에서 변경된 플로우를 걷습니다. 참조를 픽셀 단위로 정확하게 매칭해야 할 때, [Visual parity 플레이북](../../skills/poteto-mode/playbooks/visual-parity.md)은 눈으로 판단하는 대신 고정된 기준선에 대해 스크린샷을 diff합니다.
- 파서 또는 마이그레이션은 저장된 입력을 재생합니다.
- 성능 변경은 전후 프로파일을 비교합니다.
- 스토리지 변경은 기록된 값을 다시 읽습니다.

직접 검사할 수 있는 아티팩트로 증거를 요청하세요: 실패하는 테스트 그 다음 통과하는 테스트, 전후 비디오, 트레이스, 스크린샷. 수정이 이미 병합되었다면, main에서 동일한 체크를 다시 요청하세요. 아티팩트는 그럴듯한 설명보다 낫는데, 전체 실행을 재생하지 않고 도전할 수 있기 때문입니다.

완전히 신뢰하지 않는 작은 diff의 경우, [`/blast-radius`](../../skills/blast-radius/SKILL.md)는 다른 곳에서 깨뜨릴 수 있는 것을 찾습니다. 변경을 안전하게 만드는 하나의 사실을 찾고 주장이 아니라 코드를 실행하여 그 사실을 증명합니다.

## `/benchmark-checklist`로 측정된 숫자 검증

전후 숫자는 실수로 잘못 얻기 가장 쉬운 증거입니다. 따뜻한 캐시, 한쪽의 디버그 빌드, 또는 타이밍된 영역 내부에서 결코 실행되지 않은 작업은 각각 설득력 있는 속도 향상을 생성할 수 있습니다. 숫자를 보고하거나 조치하기 전에, 입력하세요:

```text
/benchmark-checklist vet the export speedup before it goes in the pr
```

[`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.md)는 7개의 질문을 하고 각각에 대한 실행의 증거를 원합니다:

1. 숫자를 제한하는 것은 무엇이며, 왜 두 배가 아닌가요?
2. 모든 측면이 프로덕션이 실행되는 방식으로 튜닝되어 실행되었나요?
3. 결과가 디스크 대역폭이나 코어 수와 같은 물리적 한계를 깨뜨리나요?
4. 무엇이든 에러가 나거나 잘못된 출력을 반환했나요?
5. 중앙값과 범위와 함께 교대 실행에 걸쳐 재현되나요?
6. 사용자가 기다리는 경로에서 엔드투엔드로 중요한가요?
7. 작업이 실제로 타이밍된 영역 내부에서 발생했나요?

판결은 실행 횟수, 범위, 제한 요소와 함께 더 빠름, 더 느림, 측정 가능한 차이 없음 또는 inconclusive로 돌아옵니다. 제한 요소를 명명할 수 없거나 한쪽이 튜닝되지 않고 실행된 경우 inconclusive라고 말합니다. `/poteto-mode`는 이미 Perf issue와 Hillclimb 플레이북 내부에서 체크리스트를 실행하므로, 그것들 밖에서 무언가를 측정했을 때 또는 다른 사람의 숫자가 너무 좋아 보일 때 직접 입력합니다. 그것은 [Explain the Number 원칙](../../skills/principle-explain-the-number/SKILL.md)의 작동 형식입니다.

## 프로젝트 검증 스킬 생성

위의 UI 항목은 실제 요구사항을 숨깁니다. 에이전트는 앱을 구동하는 스크립트화된 방법이 필요합니다. 프로젝트에 하나가 있다면, 좋습니다. 그렇지 않다면, 실행하세요:

```text
/create-verification-skill
```

[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md)는 당신이 아니라 리포지토리를 인터뷰합니다. 사용자가 건드리는 것, 앱이 로컬에서 어떻게 시작되는지, 무엇이 그것을 구동할 수 있는지(먼저 기존 하네스, 그렇지 않으면 브라우저와 CDP, PTY 또는 일반 HTTP), 어떤 증거가 동작을 증명하는지, 두 인스턴스가 나란히 실행될 수 있는지 파악합니다. 코드가 답할 수 없는 것만 묻습니다.

`.cursor/skills/verify-<app>/`를 작성하며, 정확한 Launch, Doctor, Drive, Evidence, Cleanup 섹션을 가진 에이전트 대상 지시사항, 배포하는 스크립트를 위한 Helpers 섹션, 앱이 무엇을 하는지 그리고 각 기능이 작동함을 증명하는 결과를 색인화하는 `features/` 아래의 기능 맵. 스킬은 README 인덱스와 4개의 필수 H2를 사용하는 기능당 하나의 파일을 가진 [작동하는 feature-map 예제](../../skills/create-verification-skill/references/feature-map-example/)를 제공합니다. 전달하기 전에, 생성기는 스킬을 한 번 엔드투엔드로 증명합니다: 시작, doctor 체크, 하나의 기능 구동, 증거 캡처, 정리, 그 다음 증거가 정리에서 살아남았음을 확인. 그 증거가 실패하면, 출력을 사용하지 마세요.

그 이후로, "verify it in the app"은 어떤 에이전트든 이 리포에서 설정 대화 없이 실행할 수 있는 단계입니다. 특정 형식으로 증거를 원할 때 프롬프트에 명명하세요:

```text
/poteto-mode build the bulk-archive action. use /verify-<app> to verify your changes and show me a video and screenshots as proof.
```

```text
/poteto-mode repro this with /verify-<app>. if it repros on main, fix it and show me a video as proof.
```

검증 스킬이 작동하면, [`/swarm`](../../skills/swarm/SKILL.md)이 feature-map 항목별로 전체 패스를 분할하고 결과를 집계할 수 있습니다. 검증기 스웜은 또한 충분히 큰 샘플에 걸쳐 성능 승리를 확인하거나, PR이 배포되기 전에 회귀를 위해 앱을 퍼즈합니다.

검증 스킬을 일회성이 아니라 인프라로 취급하세요. 커밋하여, 팀의 모든 사람과 모든 에이전트가 동일한 방식으로 앱을 구동하도록 하세요. 그런 다음 [레버를 빌드](../../skills/principle-build-the-lever/SKILL.md)하세요. 에이전트가 앱을 클릭하기 위해 일회용 스크립트를 계속 작성할 때, 스킬이 대신 호출하는 작은 제어 CLI를 요청하세요. 에이전트는 더 적은 토큰을 소비하고, 모든 실행이 반복 가능해집니다. 에이전트가 잘 사용하는 CLI는 이러한 특성을 가집니다:

- 많은 얇은 것보다 각각 실제 작업을 수행하는 몇 개의 구성 가능한 명령.
- 파괴적인 것에 대한 `--dry-run` 옵션.
- 모든 것을 한 번에가 아니라 점진적으로 기능을 드러내는 서브커맨드.
- 대신 무엇을 할지 말하는 에러 메시지.
- 풍부한 `--help` 텍스트.
- JSON과 같은 기계 읽기 가능한 출력.

거기 있는 동안, 개발 설정도 반복 가능하게 만드세요: 시드된 데이터, 테스트 사용자, 매번 같은 방식으로 환경을 올리는 하나의 명령.

## 검증 스킬을 정직하게 유지

앱이 변경되고, 기능 맵이 구식이 됩니다. 적어도 하루에 한 번, 이상적으로는 아무도 기억할 필요가 없도록 예약된 자동화에서 실행하세요:

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md)는 생성된 스킬을 감사합니다: 기능당 하나의 읽기 전용 소스 리더를 병렬로, 그 다음 매핑된 모든 기능을 구동하는 하나의 라이브 패스. 정확히 세 가지 결과 중 하나로 끝납니다. `clean`은 전체 커버리지와 배포할 것이 없음을 의미합니다. `changed`는 검증 스킬 자체 디렉토리에 국한된 입증된 수정의 하나의 PR을 의미합니다. `blocked`는 블로커를 명명합니다. 프로덕트 코드를 절대 편집하지 않습니다. 라이브 패스가 프로덕트 회귀를 잡으면, doc 편집으로 숨기는 대신 회귀를 보고합니다.

## 공식 검증 스킬로 속성 증명

검증 스킬은 당신이 구동하는 경로를 증명합니다. 일부 버그는 아무도 구동하지 않는 경로에 있습니다: 겹치는 두 재시도, 쓰기 중간에 만료되는 잠금, 순서대로 도착하지 않는 상태 변경. 테스트는 거의 그러한 케이스에 도달하지 못합니다. 그러한 버그가 비용이 많이 드는 코드의 경우, 실행하세요:

```text
/create-formal-verification-skill
```

[`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md)는 코드에서 대상을 선택합니다: 코드가 만드는 약속으로, 깨지면 사용자를 해치고 테스트가 거의 깨뜨리는 케이스에 도달하지 못하는 것. 검증하기 가장 쉬운 것이 아니라 가장 강력한 대상을 선택합니다. 대신 거기서 시작하도록 영역이나 버그를 명명하세요:

```text
/create-formal-verification-skill the job lease and retry logic. a job must never run twice at once.
```

질문이 도구를 선택합니다. 이벤트가 나쁜 순서로 발생할 수 있는지는 설계의 작은 모델에 대한 모델 체커에 적합하며, TLA+가 어떤 언어에서든 그것의 기본값입니다. 코드가 모든 입력에 대해 행동하는지는 코드에서 실행되는 검증기에 적합합니다. 언어에서 실행되는 검증기가 없으면, 에이전트가 그렇게 말하고 함수의 손으로 작성한 모델이 아니라 생성된 입력으로 실제 코드를 테스트합니다. 모든 크기에서 유지해야 하는 속성은 증명이 필요할 수 있습니다. 에이전트는 선택한 도구와 이유를 알려줍니다.

하나의 속성을 검증하고 코드의 손상된 변형에서 그 속성이 실패하는 것을 보여주는데, 실패하는 것을 본 적이 없는 체크는 아무것도 증명하지 않기 때문입니다. 현재 코드가 이미 속성을 깨뜨리면, 코드의 용어로 짧은 단계 시퀀스로 반례를 얻습니다. 속성은 명시된 대로 유지되므로, 발견은 발견으로 유지됩니다. 요청하지 않는 한 프로덕트 코드는 변경되지 않습니다.

다음 에이전트에게 변경이 검증된 코드를 건드리는지, 하나의 명령으로 체크를 실행하는 방법, 실제 버그를 모델링 에러와 구별하는 방법을 알려주는 프로젝트 로컬 스킬을 작성합니다. 전달하기 전에, 생성기는 속성을 깨뜨리는 스크래치 변경에서 그 스킬을 한 번 따르고, 체크가 그것을 잡아야 합니다. 핸드오프는 어떤 도구와 경계로 무엇이 검증되었는지, 체크가 무엇을 발견했는지, 커버하지 않는 것이 무엇인지 말합니다. 패스는 전체 시스템이 아니라 모델이나 경계를 커버합니다.

스킬은 또한 각 체크가 커버하는 코드와 체크가 마지막으로 일치한 커밋을 기록합니다. 스킬을 건너뛰는 병합과 리팩토링은 사라진 코드의 설명에서 통과하는 체크를 남길 수 있습니다. 그들 후에, [`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md)를 실행하세요. 코드에서 검증을 업데이트하고, 재실행하고, 각 업데이트된 체크가 여전히 실패할 수 있음을 보여주고, 각 실패가 검증의 드리프트인지 코드의 버그인지 말합니다.

## 상태도로 동작 보여주기

모델 용어의 반례는 당신을 확신시킵니다. 동작을 소유하는 PM 또는 디자이너는 그들의 용어로 볼 필요가 있습니다. 실행하세요:

```text
/statechart what the user sees when they edit a note offline
```

[`/statechart`](../../skills/statechart/SKILL.md)는 TLA+ 모델에서 생성된 사용자가 보는 것의 Mermaid 상태도를 그리므로, 그림과 체크된 모델이 떨어져 표류할 수 없습니다. 독자의 규칙("오프라인일 때 Synced를 절대 보지 않는다")은 불변식이 됩니다. 차트는 규칙을 깨뜨리는 각 상태를 표시하고, 보고서는 독자의 단어로 그것에 대한 최단 경로를 제공합니다. 핸드오프 전에, 에이전트는 실제 코드에서 각 버그 경로를 재현하므로, 모델링 에러가 버그로 독자에게 도달하지 않습니다.

## PR 열기

```text
/poteto-mode open the pr. small ordered commits, evidence in the description.
```

[PR 열기 플레이북](../../skills/poteto-mode/playbooks/opening-a-pr.md)은 워크트리에서 작동하고, 작업을 작은 순서있는 커밋으로 리베이스하고, diff를 정리하고, 산문을 unslop하고, PR 링크를 반환합니다. 5개의 좁은 PR이 하나의 뚱뚱한 것보다 낫고, 스택된 후속 조치가 성장하는 브랜치보다 낫습니다.

## Babysit으로 PR을 병합 준비 상태로 주도

열린 PR은 즉시 블로커를 수집하기 시작합니다. 체크가 실패하고, 리뷰어가 주석을 달고, 트렁크가 이동합니다. 그 이탈을 [Babysit 플레이북](../../skills/poteto-mode/playbooks/babysit.md)에 전달하세요:

```text
/poteto-mode babysit this pr. get it green.
```

Babysit은 GitHub의 번들된 감시자 또는 사용 가능한 경우 Origin CLI로 PR을 감시하고, 순서대로 블로커를 취합니다: 충돌, 그 다음 리뷰 스레드, 그 다음 CI. 알려진 모든 수정은 하나의 푸시로 일괄 처리되므로, 체크가 모든 수정 후가 아니라 한 번 재시작됩니다. 주석 분류는 회의적인데, 사람과 봇이 동일한 리스트에 실제 캐치와 노이즈를 제출하기 때문입니다. 실제 발견은 수정을 얻고, 노이즈는 스레드에 게시된 반증과 함께 기각됩니다. 상태만 원할 때, 더 작게 물어보면 Babysit이 루프를 시작하지 않고 답변합니다:

```text
/poteto-mode check on pr 123. anything outstanding?
```

Babysit은 병합 준비 상태에서 멈춥니다. 모든 것이 그린이어도 절대 병합하지 않는데, 병합은 다른 결정이기 때문입니다.

## Shipping으로 스택 착지

그린은 안전과 같지 않습니다. 착지할 준비가 되었을 때, 말하세요:

```text
/poteto-mode land the stack.
```

[Shipping 플레이북](../../skills/poteto-mode/playbooks/shipping.md)은 무엇이든 무장하기 전에 각 PR을 독립적으로 검증합니다. PR당 하나의 새로운 에이전트가 동작을 라이브로 증명하고, 변경을 판단하는 에이전트는 그것을 작성한 에이전트가 절대 아닙니다. 그런 다음 Shipping은 기본적으로 GitHub를 통해 또는 CLI가 사용 가능한 경우 Origin을 통해 한 번에 하나의 PR로 하단에서 연속된 검증된 실행만 착지시키고, 체인을 깨뜨리는 첫 번째 PR을 보고합니다. 검증되지 않은 것 위에 앉아 있는 검증된 PR은 기다리는데, 그것을 병합하면 아래에 간격을 당기기 때문입니다.
