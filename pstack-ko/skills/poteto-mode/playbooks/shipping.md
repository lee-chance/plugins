### 출시

**착륙하는 것을 당신이 소유합니다. 각 PR을 독립적으로 검증하고, 루트로부터 검증된 실행만 착륙시킨 다음, 스택에서 손을 떼세요.**

1. **Forge를 해결한 다음, 착륙 전에 각 PR을 독립적으로 검증하세요.** GitHub CLI(`gh`)가 기본입니다. `command -v origin`이 성공하고 Origin이 리포지토리를 해결할 수 있으면, 모든 PR 작업에 `origin pr` 사용. 그렇지 않으면 `gh`에 머물고 폴백을 기록. Graphite(`gt`)를 절대 요구하지 마세요. PR당 한 검증자, 각각 Cursor 클라우드 에이전트, 일치하는 제어 스킬(`cursor-team-kit`의 `control-ui` 또는 `control-cli` 같은)로 사용자가 하는 방식대로 변경을 실행하고, head에 대한 부모, 그 PR에 `PASS`, `PASS+NOTES`, 또는 `FAIL`을 게시. 코드를 작성하지 않은 에이전트의 판정만 카운트됩니다. 저자는 빌드하려고 의도한 것을 검사하기 때문입니다. 녹색 CI와 승인하는 봇 리뷰는 판정이 아닙니다. 둘 다 사용자가 하는 방식대로 변경을 실행하지 않기 때문입니다.
2. **하단에 루트된 연속 검증 실행만 착륙시키세요.** 병합되지 않은 가장 낮은 PR에서 걸어 올라가고 `PASS` 또는 `PASS+NOTES` 없는 첫 번째에서 중단. 그 아래의 PR들이 실행이고, 상단 것이 천장입니다. 검증되지 않은 것 위의 검증된 PR은 기다립니다. 그 아래의 코드 없이 착륙할 수 없기 때문입니다. 그 코드를 보유하지도 필요로 하지도 않는 브랜치를 가진 것은 trunk로 이동하고 자체적으로 착륙할 수 있습니다. 먼저 새 판정이 필요합니다. 기존 것은 그 코드가 아래에 있는 상태로 실행되었고 trunk는 그것을 가지고 있지 않기 때문입니다.
3. **판정이 여전히 코드를 설명하는지 재검사하세요.** 판정은 패치를 커버하고, 체인 리베이스는 검사 실패 없이 그 위의 모든 PR을 새 SHA로 이동시킵니다. 이전 판정을 신뢰하기 전에 판정 SHA에서 `git patch-id`를 현재 head와 비교하세요. 패치가 테스트, 문서, 또는 린트 설정에서만 다를 때, 레인이 실행한 것이 두 SHA 모두에서 노이즈를 제외하고 같게 빌드되면 레인의 결과가 유지됩니다. 노이즈는 판정 SHA의 두 빌드 간에도 나타나는 차이, 또는 내장된 커밋 SHA입니다. 독자가 호출을 검사할 수 있도록 파일과 함께 각 종류의 노이즈를 보고하세요. 변경 자체는 여전히 새 검사와 리뷰를 얻습니다. 기존 판정이 그것을 절대 보지 못했기 때문입니다. dev 서버 같이 빌드 출력이 없는 레인은 이것을 보여줄 수 없으므로, 그것을 재실행하고, 드리프트한 다른 것도 재검증하세요.
4. **하단부터, 한 번에 하나의 PR씩 착륙시키세요.** 항상 실행의 병합되지 않은 가장 낮은 PR을 병합하세요. `origin pr merge <pr>` 또는 `gh pr merge <pr> --squash`로. Origin에서 평범한 명령은 당신이 명명한 것 아래의 모든 PR도 병합하고, GitHub에서 베이스가 여전히 부모의 브랜치인 PR은 trunk가 아니라 그 브랜치로 병합합니다. 결과에 대해 PR을 다시 읽으세요(`origin pr view <pr>` 또는 `gh pr view <pr> --json state,mergedAt,baseRefName`). 병합 명령은 병합 큐가 PR만 큐에 넣었을 때 성공을 보고할 수 있고, 요청된 auto-merge는 병합이 아니기 때문입니다. 착륙한 PR은 부모의 브랜치가 아니라 trunk를 베이스로 하여 병합된 것으로 읽습니다. 판정이 현재 head를 커버하는 PR에서만 `--auto`(Origin merge-when-ready 또는 GitHub auto-merge)를 준비하세요. 준비된 head가 무엇이든 착륙하기 때문입니다. 병합이 착륙한 후, 베이스가 병합된 브랜치였던 PR을 trunk로 재타깃하고(`origin pr edit <pr> --base <trunk>` 또는 `gh pr edit <pr> --base <trunk>`), 그 패치를 병합 결과로 옮기며, `--force-with-lease`로 푸시하세요. 판정은 커밋이 아니라 패치를 커버하므로, 3단계의 patch-id 규칙이 판정이 살아남는지 결정합니다. 검사가 통과하고 판정이 살아남으면 병합하세요.
5. **착륙하는 동안 스택을 그대로 두세요.** 4단계의 다음 PR 이동이 브랜치나 베이스에 대한 유일한 변경입니다. 병합은 그 순간 그 브랜치와 베이스가 보유한 것을 착륙시키기 때문에, 판정 여부와 무관합니다. GitHub에서는 `playbooks/babysit.md`의 큐된 감시자(`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`)로 `/loop` 하에서 천장에서 `COMPLETE`를 보고할 때까지 실행을 감시. Origin에서는 천장이 병합된 것으로 읽을 때까지 `origin pr checks <pr> --watch`가 반환할 때마다 `origin pr view <pr> --checks`로 현재 PR을 다시 읽으세요. 부모가 병합될 때 trunk로 이동하는 베이스는 수리할 손상이 아니라 예상됩니다. 병합이 정체되면, 무언가를 변경하기 전에 이유를 찾아내세요.
6. **천장에서 중단하세요.** 실행을 확장하는 것은 새 판정을 필요로 하므로, 1단계를 통한 새 패스입니다.

**답변:** 검증된 실행과 그 천장, 각 PR의 판정과 누가 생성했는지, 착륙한 것과 어떻게 확인했는지, 다음 갭이 필요로 하는 것.
